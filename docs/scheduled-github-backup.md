# Scheduled GitHub backup

Connect GitHub through Branch's existing integration, using a token or GitHub App with **Contents: read and write** for a private repository. The app must have an initial default branch. In an owner-started conversation, call `backup.github_configure` with the private `owner/repository`, `enabled: true`, and `hours` from 24 to 720. Confirm the destination and recurring export. Backups begin after that interval and run only while Branch is open; missed intervals produce one backup, not a catch-up burst.

The snapshot contains the owner's current memory facts, installed skill documents and versions, and the existing catalogue of safe settings. It excludes conversations, credentials, sign-ins, devices, trust records, workspace files and automation consent. Recognised embedded credentials and known runtime secrets are scrubbed. This is not an encrypted archive: other private-repository collaborators can read the remaining memory and skill text. Arbitrary unrecognised secrets written into free text cannot be categorically detected.

Each snapshot is a new JSON file under `branch-agent-backups/`, committed through GitHub's Contents API. No owner checkout, git history, existing remote file or branch is force-replaced. Repository identity, privacy, write access, network policy, Lockdown, schedule consent and connection continuity are checked. The schedule pins the project used for GitHub credentials. A failure is shown by `backup.github_status`; the next retry is the approved interval. Bounds are 128 KiB, 10,000 current memory records, 50 installed skills and 1,000 skill versions. Oversized snapshots fail rather than sending a partial copy.

Use `backup.github_status` to obtain the last successful snapshot `id` and exact `commit`. `backup.github_inspect` validates that pin and shows counts without modifying live state. `backup.github_restore_prepare` asks once before downloading and writing a fresh recovery directory in Branch's data folder. It produces `backup.json` for the existing **fresh-install backup restore**, plus `settings.json` for the existing settings import and proposal review. Skills in the archive are inactive and require review before activation. Preparation reports `restored: false`: it never replaces the currently running app's state or workspace.

To stop recurring uploads, call `backup.github_configure` with `enabled: false`. The destination and recurring consent are never restored from another backup. Historical files on GitHub remain; delete them yourself if appropriate. This patch has no provider/account or installed-app validation yet.

For direct recovery, `backup.github_restore` takes the same exact snapshot pin and asks once before applying the existing restore consumer to a freshly generated empty directory under Branch's data folder. It cannot take an arbitrary destination or reuse an existing directory. Memory and inactive skills are restored into `branch.sqlite`; validated catalogue settings enter the existing restored-settings review queue. It returns `restored: true` for that new directory, leaving the running install untouched. Start a separate Branch instance with `BRANCH_DATA_DIR` set to the returned folder, then review configuration and skills in that instance. No provider/runtime recovery was executed while developing this code.

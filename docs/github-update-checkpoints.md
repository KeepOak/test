# Encrypted pre-update GitHub checkpoints

SELF-053 is opt-in. Settings → Updates → More → GitHub update checkpoints previews a dedicated, initialized private repository, its numeric repository ID, one project/secret name, an RSA recovery public-key fingerprint, and the original-file byte limit. The owner confirms that the repository is dedicated and that the matching private key is retained outside Branch. A ten-minute, single-use preview authorizes this exact scope. No repository is created automatically. Use a fine-grained token restricted to Contents read/write for this one repository; Branch cannot prove that a supplied token has no unrelated grants.

Authorization is a local updater-owned sidecar under `update-backups/github-checkpoint`, excluded from the actual data copy and ordinary database imports. There is no settings-kit writer, task tool, phone grant or remote enrollment route. The owner may explicitly disable the requirement. Malformed authorization fails closed. The enrollment API, upload callback and recovery require the owner locally, an unlocked session and Lockdown off. Scope is rechecked before each GitHub request. Only the exact configured project/secret is resolved; no locker listing or blanket export occurs.

The deployment safety-copy endpoint first creates the existing row backup and finalized `takeDataCopy` directory. Only that named copy is archived. The updater awaits an encrypted remote commit and readback before replacing application files. Missing token, changed/private-to-public target, locked session, unavailable network, limits, links, unstable files, unrelated checkpoint-branch files or failed verification hold the update. The offline headless path makes local copies and then holds a configured update until the owner starts and unlocks Branch; it never opens the locker to bypass that hold. Unconfigured updates retain local safety copies.

Each archive uses a fresh 256-bit AES-GCM key and 96-bit nonce, with a 128-bit authentication tag. RSA-OAEP-SHA256 wraps the AES key for the owner's 3072–16384-bit public key. Associated data binds the envelope version, random checkpoint ID, pinned repository ID and recipient fingerprint. All original filenames, local-copy name and file contents are inside the ciphertext. The remote envelope exposes only format/opaque identity, cryptographic metadata, chunk sizes and hashes. No private recovery key is uploaded. Memory buffers holding plaintext and AES keys are cleared where practical; JavaScript strings and KeyObjects cannot be reliably zeroed.

GitHub receives only `envelope.json` and bounded encrypted `chunks/NNNN.bin` blobs in `branch-update-checkpoints`, never the repository's default branch. Each blob's Git object SHA and readback digest is verified. New trees contain only checkpoint files. Commits extend the previous verified checkpoint commit, use a generic identity/message with `[skip ci]`, and update the exact ref without force. Ref, tree, chunk digests, repository ID and privacy are checked after publication. Repository-visibility changes cannot be locked atomically with a Git update; ciphertext still protects content, and detected changes hold the application update. Branch does not change repository permissions, retention, workflows or billing. The repository must remain dedicated and owner-managed; GitHub's existing workflows and storage policy remain the owner's responsibility.

Recovery uses the enrolled repository ID and public-key fingerprint, the latest fixed-branch commit or an exact owner-selected SHA, and one absolute owner-selected private-key file. A two-minute, single-use preview binds the exact commit, ciphertext digest, recipient, authorization and key-file path before the owner confirms reading it. The key is read locally and must derive the enrolled fingerprint. The current route accepts an unencrypted PEM key file; passphrase handling is not implemented. Verified ciphertext is authenticated/decrypted before any staging. Paths, case/Unicode collisions, bytes, hashes, file count and filesystem types are checked. Recovery creates a fresh local data-copy restore point. The existing data-copy controls provide the separate decision to restore at next start; this API never replaces live work. On a new device, initialize Branch, store the restricted token, enroll the original private repository/public key, and retain the original recovery private key before staging an old checkpoint.

## Bounds and acceptance gaps

- Maximum 64 MiB of original file bytes, 5,000 file/directory entries, 96 MiB serialized ciphertext, 24 chunks of at most 4 MiB, 6 MiB per API response, 20 seconds per HTTP request, three minutes per remote operation; archive/staging check a 30-second budget between filesystem entries. Bounds hold rather than omit files.
- Symlinks, hard-linked files, special files and nonportable Windows paths are refused. File bytes and empty directories are preserved; recovery uses private modes rather than original ACLs, timestamps or executable bits. Existing whole-copy exclusions remain: model caches, updater state, activation records, running/session tokens, and SQLite side files. Device-bound files that the actual copy includes are encrypted too. Moving to a different OS/device may require existing locker/account recovery; a staged copy is not certification that credentials are portable.
- Caught recovery failures clean only the newly created, path-verified staging directory. Process termination or refused cleanup can leave an unavailable `.partial` directory, protected from task reads. Owner restore routes retain internal access; live owner data is never deleted. Previous remote ciphertext remains in Git history; disabling enrollment does not erase it. No GitHub retention/garbage-collection mechanism is implemented.
- The trust boundary is Branch's protected updater directory and local owner authorization. Hostile code already executing as the same OS user is outside that boundary. Windows file mode flags are not a complete ACL-hardening mechanism. An external same-user filesystem writer can still race directory operations; use the existing local app data directory protections.
- `tests/github-checkpoint-archive.test.mjs` proves the encrypt/recover round trip, that no file name or content leaves in the clear, and that a wrong key is refused. GitHub ref races and visibility changes, interruption, large-copy limits, updater integration and cross-device restore are not covered by tests.

## Source provenance

Existing Branch `install/data-copy.ts`, `install/update-backup.ts`, `install/headless-update.ts`, `deployment-api.ts`, `git-checkpoint.ts`, `vault.ts`, network policy, update IPC and restore controls were inspected. Existing draft #1035 offers an owner-reviewed checkpoint task; it explicitly does not create/upload a checkpoint. This mechanism complements that offer and does not replace its exact-release hold.

The actual [Hermes checkpoint manager](https://github.com/NousResearch/hermes-agent/blob/main/tools/checkpoint_manager.py) and MIT license, and [Gemini CLI Git service](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/gitService.ts) and Apache-2.0 license were read. They implement local shadow Git checkpoints, which cannot safely substitute for encrypting the actual finalized application data copy; no source was copied and no dependency added. The implementation follows the primary [GitHub blobs](https://docs.github.com/en/rest/git/blobs), [trees](https://docs.github.com/en/rest/git/trees), [commits](https://docs.github.com/en/rest/git/commits), [refs](https://docs.github.com/en/rest/git/refs) and [Node crypto](https://nodejs.org/api/crypto.html) contracts.

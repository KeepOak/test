# Exact native window watches (SCREEN-072, partial source delivery)

`desktop.nativeTargets` discovers native IDs and `desktop.watchNative` accepts an exact returned target. The existing screen switch, approval permission (`desktop.view`), OS permission check, visible Stop notice, cancellation, Take over and per-run action allowance still apply. Approval target text includes all target, exclusion and watch terms. A watch captures at most 20 frames within 30 seconds, reports PNG fingerprints and keeps only the latest frame in the existing private artifact store. It does not install, build, download or start a background watcher.

On macOS 14+, `src/native-capture/macos.swift` uses ScreenCaptureKit `SCShareableContent` for discovery, `SCContentFilter(desktopIndependentWindow:)` for one window, or `SCContentFilter(display:excludingWindows:)` for an exact display with up to 32 excluded windows. `SCScreenshotManager.captureImage` reads the filtered native content. No whole-screen crop or later redaction is labelled exclusion. Excluded IDs, PID, title, program and bounds are checked against fresh OS discovery before and after each capture. Closing, moving, resizing or changing a selected/excluded window stops the watch. This is a filter for this capture only, not a systemwide prohibition on other apps capturing those windows. No automatic claim is made that all present/future Branch viewer windows are excluded.

On Linux X11, `src/native-capture/linux-x11.c` discovers mapped EWMH windows, validates exact metadata, requests automatic XComposite redirection and reads only that window's named pixmap with XGetImage. Other desktop/overlapping window pixels are not read through a root-screen crop. Captured content includes the selected window hierarchy/embedded child windows; this is not a guarantee of a single isolated application identity. Window content and bounds are checked again before output. Display capture with arbitrary window exclusions is explicitly unsupported. Wayland, XWayland fallback in a Wayland session, headless sessions, missing EWMH metadata, non-TrueColor windows and absent XComposite 0.2+ are refused. X11 `_NET_WM_PID`/titles are client metadata, not cryptographic process attestation.

## Owner preparation, outside this delivery

Prepare and review the appropriate helper as a regular executable writable only by its owner, then launch the engine with its absolute `BRANCH_NATIVE_WINDOW_CAPTURE` path and lowercase `BRANCH_NATIVE_WINDOW_CAPTURE_SHA256` digest. Branch checks the digest before every bounded helper process. No helper is bundled or executed by this change; no install is attempted when it is missing. Changes to the binary require new owner preparation. The hash check trusts the owner-controlled executable path; it is not an adversarial same-user filesystem race defence.

Mac source requires a macOS 14+ SDK/runtime and the helper's actual Screen Recording permission. A future owner-authorized build can use `swiftc -parse-as-library src/native-capture/macos.swift -o <prepared-path>` with the SDK frameworks available. The helper must receive its own permission; an engine grant is not proof the helper can capture.

Linux source requires owner-prepared Xlib/XComposite, json-c and libpng development/runtime libraries. A future authorized build can use `cc src/native-capture/linux-x11.c -o <prepared-path> $(pkg-config --cflags --libs x11 xcomposite json-c libpng)`. These are native helper prerequisites, not new npm dependencies. json-c parses bounded request data; libpng encodes genuine drawable pixels. Its executable must be launched in the owner's actual X11 session. Existing bounded child-process environment supplies DISPLAY/XAUTHORITY without provider secrets.

Helpers receive one bounded JSON argument, emit protocol-1 JSON metadata and write one private temporary PNG. The driver rejects wrong platform, method, changed terms or output over 20 MB. Display captures retain conservative refusal for visible password/sign-in windows, even when a user asks to exclude one. Temporary PNGs are removed in `finally`; only the latest approved frame is retained.

## Validation and gaps

Source inspection and `git diff --check` only. No native helper, compiler, tests, build, desktop, screen permission flow, runtime, provider or model was executed. Native compilation, SDK availability, TCC permissions, X server/compositor behaviour and exact-commit capture/exclusion acceptance remain unverified. GPU/protected surfaces can fail or return an empty/native-black frame; no screen fallback is taken and this source does not certify frame usefulness.

SCREEN-072 remains partial: Mac native filtered exclusion source exists, Linux exact window capture exists, Linux arbitrary display exclusion/Wayland support do not. The owner's live viewer/phone port has not been connected to these new tools; Windows authenticated CaptureLease/content-protection behaviour is unchanged. Existing #603 trusted native port and the independent private Linux sandbox must be preserved when integrating, rather than replacing their scope checks.

Reviewed references: [Apple SCContentFilter](https://developer.apple.com/documentation/screencapturekit/sccontentfilter), [SCScreenshotManager captureImage](https://developer.apple.com/documentation/ScreenCaptureKit/SCScreenshotManager/captureImage(contentFilter:configuration:completionHandler:)), [X.Org XComposite specification](https://www.x.org/archive/X11R7.5/doc/man/man3/Xcomposite.3.html), Hermes `tools/computer_use/cua_backend_capture.py` and OpenClaw `ComputerWindowActionExecutor.swift`, with both upstream MIT licences read. Their existing target-discovery/stale-reference ideas were reviewed; their larger backend/action implementations were not copied as substitutes for OS filtering. New helper code calls the documented native APIs directly.

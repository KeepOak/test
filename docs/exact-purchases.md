# Exact scoped purchases (RES-115 / RES-116)

This initial source path is intentionally narrow: Stripe Link shared payment tokens for one Stripe MPP `charge` challenge at an owner-enabled HTTPS GET endpoint. USD integer cents only, up to 100,000 cents per purchase. Full checkout forms, cards/PANs, subscriptions, POST bodies, redirects, URL queries, shipping, other currencies and other payment methods are unsupported. Runtime acceptance is unverified. The implementation was not installed, executed or connected to a wallet during delivery.

Settings → Accounts → Exact purchases starts off. The owner supplies a named secret holding an existing authorized Link access token, an explicit Link payment-method ID, exact seller origins and the scope acknowledgement. No token value is displayed or read during configuration. Obtaining/refreshing a Link grant remains an external owner setup step; there is no automatic login, wallet funding or card selection. This computer's purchase configuration stays out of ordinary backup/export. Live quotes and authorization grants exist only in memory; restart, setting changes and app lock invalidate them.

`payments.quote` gets an actual HTTP 402 challenge through Branch's network policy. A successful HTTP response alone is never interpreted as a free price. Quotes retain a fixed destination, challenge hash, exact USD amount/currency/network and expiry. Item and seller labels are supplied by the owner/task and are not verified inventory or legal seller identity. The challenge is untrusted pricing information, not an invoice-total guarantee.

Paid amounts always require the owner's exact three-minute single-use authorization in the purchase UI, followed by Link approval. The optional zero-amount condition removes only the additional money authorization prompt: all existing tool, write, source, permission, Lockdown, authenticator-code and network gates remain. An owner-facing manual tool action cannot supply an authenticator code: where enabled, use the existing conversation approval card after authorizing the exact quote. Other profiles, keys, channels, shared/temporary conversations, helpers, Trunks and isolated work cannot purchase.

`payments.spend` consumes the local authorization before provider work, re-probes the pinned destination and requires the identical challenge. A Link spend request uses that authorization ID as its provider idempotency key, the exact amount, network, method and seller URL. No merchant body or payment credential is logged or returned. Pending Link approvals are shown for an explicit `payments.complete` operation within the original scope/expiry; there is no background polling or automatic continuation. The approved request is checked again and its shared payment token is released only to the pinned destination. Redirects and changed challenges are refused, including nonce/expiry changes. A changed challenge requires inspection and a new quote/authorization, never an automatic new purchase.

The receipt separates requested amount, merchant HTTP response, merchant receipt-header hash, wallet payment status/charged amount and fulfilment. Only a wallet `succeeded` readback with an exact successful charged amount/currency is marked `payment-recorded`; delivery and invoice total remain unverified/unknown. Missing/stale readback, timeout, cancellation, denial, provider failure or a mismatch does not become successful purchase evidence. An ambiguous attempt consumes its authorization and records `unknown`; inspect Link before any new approval. A restart does not recover or retry outstanding spend requests. Remote revocation and wallet reconciliation depend on the provider's readback; no final invoice-total, refund or fulfilment guarantee is made.

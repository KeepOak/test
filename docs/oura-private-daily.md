# Private Oura daily summaries

The requested RES-129 travel row does not exist in `8-research.md`: RES-128 is followed by RES-130. No TravelCompositor requirement or existing travel implementation was found. This authorized fallback implements a concrete part of RES-118 (health/wearable data): owner-window Oura daily summaries.

The composer + menu opens private Oura controls. Default is off. The owner supplies their registered Oura app client ID, existing client-secret locker reference and an unprivileged fixed loopback callback port, saves explicit enabled configuration, then authorizes Oura. Only `daily` is requested: sleep, activity and readiness. Email, personal demographics, heart-rate series, workouts, tags, sessions and SpO2 are not requested. No personal-access-token path is added; Oura documents PATs as deprecated.

Oura requires an exact registered redirect. The owner registers `http://127.0.0.1:PORT/oauth/callback`. The only shared OAuth seam is optional `start(provider,{loopbackPort})`, validated as an integer from 1024 to 65535; existing callers keep ephemeral ports. Loopback binding, state/PKCE, service-returned expiry, timeout and cancellation remain the existing implementation. The owner opens the returned service URL themselves. No automatic browser or sign-in execution occurs here.

Changing any connector configuration or disabling access creates a new local grant identity and cancels the old pending flow. Old encrypted tokens cannot be reused by the new configuration. Disable is local revocation, not deletion/revocation of provider app permission: the owner must revoke the old application in Oura. Late callbacks to obsolete grant IDs cannot authorize current reads. The connector never refreshes Oura's single-use refresh tokens automatically; reaching returned expiry requires a new explicit authorization. Private reads are serialized.

Status reports actual saved-token presence, returned expiry and returned scope without claiming live connectivity. A null returned scope remains unknown; it is not filled with the requested daily scope. If a returned grant explicitly excludes daily, reads fail and require reconsent. Oura resource endpoints enforce the actual grant when scope metadata was omitted.

Each owner press approves an ordered real-calendar date range of at most 31 days. The connector requests only day/score and activity steps from `daily_sleep`, `daily_readiness` and `daily_activity`, follows at most two pages per collection, validates bounded rows and marks remaining pages as truncated. Fixed HTTPS Oura hosts, guarded Branch fetch/network policy, no redirects, 20-second request timeouts and 256KB streaming response limits apply. Owner/profile/person/short-key/Lockdown/app-lock/local-window restrictions are rechecked across awaits and immediately before resource requests. The API isn't registered as a model tool. Metrics are not saved in Branch or automatically sent to a model.

The window renders private raw daily scores and steps, not clinical interpretation. An empty or missing score can reflect sync, unavailable measurements, consent or membership; it does not establish a denied grant. Gen3/later users may require active Oura Membership, and API applications are limited to ten users before provider approval. No free-service/API-pricing assertion is made; price and commercial approval are unverified. Owner app registration and credentials must be prepared separately.

RES-118 remains partial: Whoop, Fitbit, Apple Health and Health Connect are not implemented. Native/device permission bridges are needed for the latter two. This increment provides no clinical advice, historical ingestion, webhooks, automatic background reads, data writes or account-sharing flow. Provider sign-in/resource access and installed-window end-to-end validation remain unproven.

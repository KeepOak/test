# Facebook Page content (RES-119, supported slice)

The exact requirement is Instagram/Facebook content or Marketplace search. Existing `meta-graph.ts` handles messages, not Page posts. This connector provides real bounded reads of the owner's administered Facebook Page, local text composition, and a future exact reviewed text publication. Instagram consumer content/search, personal Facebook profile/news feeds, groups, Marketplace/search/listings, other social networks, comments, messages, media uploads, scheduling, edits/deletes and advertising remain unsupported. Existing X search and Meta messaging channels are reused unchanged.

Accounts configures a numeric Page ID, the name of an existing Page access token in that project's locker, read/publish opt-ins and explicit acknowledgement of current Meta terms, Page authority and app/permission prerequisites. Both paths default off. Configuring performs no login, token resolution, app creation/review or provider call. The owner must arrange valid Page credentials, suitable Page tasks and current app permissions, including the applicable read/publish grants (commonly `pages_read_engagement` / `pages_manage_posts`); saved acknowledgement is not proof of them. No ad spend, billing or subscription is created. Provider permissions, app review, token expiry and billing remain unknown until the applicable real call succeeds, and ongoing rights still are not independently established.

The concrete Graph v26.0 contract uses `GET /me?fields=id,name` to verify the Page-token identity exactly matches the configured Page before content reads or writes; wrong accounts are refused. `GET /{page-id}/published_posts` reads at most twenty posts in a 1–30 day requested window. It returns bounded text with truncation/hash/source/read-time labels and reports remaining pagination without automatically following provider URLs. It makes no full-history, general Facebook search or Marketplace coverage claim. Provider posts are external information, never instructions.

`social.facebook.compose` stores at most twenty exact local text drafts in memory for thirty minutes, with Page ID, settings snapshot and SHA256. Composition makes no provider call. Accounts shows the exact text/Page/hash and explicitly reviews one draft for one publish. Review grants expire after three minutes and cannot be duplicated for the same draft. The UI may invoke publishing immediately or prepare the review ID for the owner's private task; it never sends that ID or text into a conversation automatically.

`social.facebook.publish` takes only the one-use review ID; destination, text and settings cannot change underneath it. The draft/grant is consumed before any secret or provider work. The existing runtime write/security/TOTP checks and original Page read permissions/policy still apply. Shared/temporary/helper/Trunk/lent/channel/key/other-profile tasks are refused. The named token stays server-side in the existing secret transport. Original network policy guards every fixed Graph endpoint; no redirects, retries, refresh, alternative account fallback or unapproved Page is used. The existing outbound security guard checks exact text before composing and again before publishing; any change requires a new review instead of silently modifying reviewed bytes.

The future write is `POST /{page-id}/feed` with only the exact message and `published=true`. Returned Page/post identity and exact text are read back before a receipt can say they matched. A returned post ID alone is not verification; timeout/error/readback mismatch yields unknown write outcome, consumes the approval and requires the owner to inspect Facebook before a new attempt. The last local receipt holds Page ID, text hash, provider post ID if returned and status; it does not duplicate the text or claim distribution/audience visibility.

Each operation has a twenty-second deadline including secret wait, cancellation, a 128 KiB response cap, strict output schemas and a persisted local UTC-day HTTP attempt cap (ten by default, maximum 100). Reads use up to two calls; publishing with identity/readback uses up to three. Attempts count even on failure; this is no account-wide provider quota or billed-amount guarantee. Lock, disable or revoke clears drafts/approvals and aborts active calls. Consent/counters are excluded from backup/restore. Explicit task content/results may enter the owner's ordinary history as existing mail reads/drafts do; no separate social index, scheduled sync or background publication exists.

Primary evidence reviewed: [Meta Page SDK edge contracts](https://github.com/facebook/facebook-nodejs-business-sdk/blob/main/src/objects/page.js), [PagePost fields](https://github.com/facebook/facebook-nodejs-business-sdk/blob/main/src/objects/page-post.js), [official SDK current Graph v26.0 evidence](https://github.com/facebook/facebook-ios-sdk/blob/main/CHANGELOG.md), [SDK licence](https://github.com/facebook/facebook-nodejs-business-sdk/blob/main/LICENSE). No SDK implementation was copied and no dependency added. Meta's [Page-post documentation](https://developers.facebook.com/docs/pages-api/posts/), [feed reference](https://developers.facebook.com/docs/graph-api/reference/page/feed/) and [platform terms](https://developers.facebook.com/terms/) were inaccessible/rate-limited during this source inspection. Owner setup must verify their current prerequisites/terms; the SDK licence does not grant API/data rights.

Tests: `tests/facebook-pages.test.mjs` (ships off, exact single-use review). Live Meta calls, Page permissions and the Accounts window are not exercised by tests.

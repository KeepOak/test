# Building and retaining capabilities

Branch now connects several learning and recovery paths to its existing tools and permissions. These features do not guarantee that a model can solve every task, and passing fixture tests is not evidence of universal improvement.

| Capability | Entry point | Evidence required |
| --- | --- | --- |
| Build a missing capability | Ask Branch; source changes appear in the approval inbox | Generated tools pass retained examples; source changes follow the approved contract and protected merge checks |
| Learn a browser procedure | Take control of the browser, then **Record demonstration** | Preview a complete supported journey; replay checks current permissions |
| Learn an API call | Controlled browser, **Learn an API** | Select traffic shape, supply fresh inputs, check expected response fields, then install the tested skill |
| Evaluate and restore a plugin | Plugin controls, **Evaluate and restore** | Execute candidate fixtures in isolation, compare with the available baseline, and bind promotion to unchanged source and permissions |
| Learn writing and design preferences | Feedback on an assistant reply | Explicit explanation or edit, validated model interpretation and inspectable evidence |
| Continue elsewhere | **Other computers**, continuity controls | Paired destination, source quiescence, durable ownership receipt and destination permissions |
| Recover GitHub publication | Source publication status in the inbox | Exact approved commit, destination and contract remain valid; reconcile remote state before retry |

## What learning retains

Browser recordings retain semantic navigation, labelled fills and button/link clicks. A recording is limited to one tab and twelve supported steps. Ambiguous, secret-bearing or unsupported actions make the preview incomplete and prevent saving. A saved profile can provide a separate sign-in prerequisite; credentials are not recorded into the procedure. See [demonstrations](browser-demonstrations.md).

API learning records selected request field names, not browser cookies, captured values or response bodies. It supports GET and flat string-valued JSON POST requests. Tests use explicit inputs and expected response fields; a POST requires approval of the exact test request. Installation leaves the skill disabled. See [API learning](browser-api-learning.md).

Preferences come from explicit feedback, not merely from a successful task. They are scoped to the owner, project and assistant, and can be inspected, corrected or forgotten. Later tasks in the same conversation read the current preferences. See [taste learning](taste-learning.md).

## Recovery boundaries

Plugin evaluations compare executable tool fixtures. A passing candidate must satisfy the full suite without regression; an unchanged score is not a measured improvement. Provider-only or other plugins without applicable tool fixtures cannot claim a passing tool evaluation. Promotion leaves activation as a separate owner action.

Continuity uses an already paired Branch engine. Ownership remains held locally if a remote reply is uncertain; returning ownership requires confirmed remote quiescence. This does not provision a KeepOak computer or silently export memory and credentials. An interrupted destination does not automatically repeat actions with unknown outcomes.

Publication recovery preserves the local commit and reconciles the remote branch and pull request before retrying. It requires the original source project and approved pins to remain valid. Cancellation does not delete a branch or pull request already created. See [publication recovery](self-development-publication.md).

A merged change is not necessarily present in an installed desktop build. Release and live destination acceptance are separate checks.

## Discovering capabilities before refusing work

Requests about settings, skills, installation or changing Branch preload relevant tools the task is permitted to discover. Disabled tools stay disabled and the existing context budget applies. The model is guided to inspect current settings, tools and compatibility, act within the task's authority, check the result, and retain verified lessons.

An action request that receives an unsupported first-person inability claim before any tool use gets one corrective discovery attempt. Repeating the claim without checking ends the task as unfinished. Explicit permission refusals, tool results, explanation or writing requests, dry runs, isolated graders and sealed learning tasks are excluded. This does not grant another task's permissions or credentials, or guarantee every model will follow the guidance.

# Daytona cloud workspace

Settings → Computer → Set one up opens Where, Sign-ins and Check. Choose Daytona region, an existing snapshot and a destruction deadline of 5–60 minutes; select a key name already saved in the owner's locker. Check calls the fixed account metadata endpoint and creates nothing. Review creation displays that this is a paid, disposable resource with provider billing and no guaranteed dollar ceiling. Only explicit local owner confirmation consumes the two-minute creation proposal. There is no automatic startup provisioning or model tool that creates resources.

The separate cloud backend uses the current official [control-plane OpenAPI](https://www.daytona.io/docs/openapi.json), [toolbox OpenAPI](https://www.daytona.io/docs/toolbox-openapi.json), [sandbox lifecycle documentation](https://www.daytona.io/docs/en/sandboxes/) and [process API examples](https://www.daytona.io/docs/en/troubleshooting/). It independently implements those contracts using the existing network policy fetch guard; no SDK dependency or upstream implementation code is copied. The OpenAPI declares Apache-2.0. The Daytona clients SDK source and its license split were inspected; no CLI/AGPL code is reused.

Creation requests a private sandbox with blocked outbound networking, no host mounts, inherited environment, provider secrets or volumes, five-minute idle stop, immediate deletion on stopping, and a provider-enforced wall-clock TTL. The API key is used only at the fixed control-plane and toolbox service origins and is never injected into the sandbox. Creation metadata is saved before POST, including a unique name and identity label. A timeout or malformed response keeps that recovery record; Refresh looks up that exact name and never repeats creation. A missing uncertain creation remains blocked for manual dashboard inspection rather than risking a second paid resource.

The registered `daytona.run` tool and wizard command form use `remote.execute` through the existing policy gate. The exact saved workspace name forms part of the approval arguments. Before executing, Branch verifies its provider identity label, privacy, network block, idle deletion and destruction deadline. Only started, bound, unexpired workspaces run commands; none are automatically restarted. Commands use the cloud shell, with a maximum 60-second provider timeout and bounded response reads. Owner profile, App Lock, Lockdown and network policy are checked around asynchronous boundaries. Lifecycle controls require explicit local review and the exact saved name. Delete remains pending until Refresh observes its absence; a successful DELETE reply alone is not completion proof.

This backend is a separate remote workspace, not a mounted local `SandboxHandle`. It does not copy project files, collect outputs, route an entire conversation or Trunk, offer desktop viewing, install Hermes, or run background sessions. Stop deletes this disposable workspace; hibernation/resume and retained snapshots are not implemented. Aborting the local HTTP wait is not proof that the remote command stopped; provider timeout, auto-stop and TTL remain its bounds. Snapshot resources and prices are provider-managed and are not a strict per-task cost or CPU budget. KeepOak and Modal execution remain unavailable. No authenticated provider, UI, resource creation, command, cleanup, test or build was executed during this source-only delivery.

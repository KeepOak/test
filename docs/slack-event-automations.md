# Slack event subscriptions (CHAT-165)

Settings → Chat apps → Slack event automations configures owner subscriptions. Every rule explicitly names a configured Slack connection ID and an existing inbound trigger UUID. Channel, sender, reaction and text filters narrow matches. Legacy rules without a connection remain inert until reviewed. `off` disables admission, `when-needed` queues matches for owner confirmation, and `on` uses the existing trigger policy immediately. Waiting events expire after five minutes and recheck current filters and sender authorization when run.

The existing Slack adapter uses authenticated Socket Mode (`apps.connections.open`), not an HTTP Events endpoint. Slack's Socket Mode envelopes do not use the HTTP signing-secret verification contract. Only `events_api` envelopes received on that connection with a bounded event ID and recent event_time can dispatch automations. IDs are claimed synchronously before dispatch and retained in the owner Store for ten minutes, capped at 1,000; full or malformed replay state refuses admission. This avoids duplicate dispatch over reconnect/restart without adding a second webhook source. No bearer token or event field grants owner/tool authority. Event text stays explicitly marked untrusted and execution stays in `Triggers.fire` with its existing rate/enable checks and runtime policy.

No Slack HTTP ingress is added. Any future HTTP Events endpoint must verify Slack's v0 HMAC over exact raw bytes and a five-minute request timestamp before parsing or admission. Existing generic webhook security/replay PRs #1121 and #1132 are untouched.

Primary source reviewed: [Slack Bolt SocketModeReceiver](https://github.com/slackapi/bolt-js/blob/main/src/receivers/SocketModeReceiver.ts), MIT ([license](https://github.com/slackapi/bolt-js/blob/main/LICENSE)). Branch uses its own adapter and trigger implementation; no upstream code copied. No tests, builds, Slack/provider calls, database or credential access were performed during delivery.
